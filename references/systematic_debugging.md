# Flutter Forge Reference - 系统化调试方法论

S4 实现阶段遇到 bug、测试失败或异常行为时，按本文档四阶段流程执行。禁止未调查根因就写修复代码。

## 铁律 [Rigid]

```
NO FIX WITHOUT ROOT CAUSE INVESTIGATION FIRST
未在根因调查完成前，禁止写修复代码。
```

违反铁律的后果：修复的是症状不是根因，引入新 bug 的概率远高于系统性调试。

## 适用范围

- 中等及以上任务在 S4 中遇到的任何技术问题（测试失败、构建错误、运行时异常、布局溢出、状态不一致等）
- 轻量任务和 ff-fast 未升级路径：豁免四阶段流程，但仍需定位根因后再修复（不做随机修改）

## 四阶段流程

### 阶段 1：根因调查（Root Cause Investigation）

**在尝试任何修复之前：**

1. **完整读取错误信息**
   - 不跳过错误或警告
   - 完整读取 stack trace
   - 记录行号、文件路径、错误代码
   - Flutter 特有：关注 Widget 树 dump、RenderFlex 溢出信息、setState 时序

2. **稳定复现**
   - 能否可靠触发？
   - 具体步骤是什么？
   - 每次都发生吗？
   - 如果不可复现 → 收集更多数据，不猜测

3. **检查近期变更**
   - 什么改动可能导致了这个问题？
   - Git diff、最近提交
   - 新增依赖、配置变更
   - 环境差异（Flutter 版本、SDK 版本）

4. **追踪数据流**
   - 错误值从哪里来？
   - 谁传了这个值？
   - 持续向上追踪直到找到源头
   - 修复源头，不是修复症状

5. **Flutter 专项定位**
   - 布局问题 → 检查约束传递链（parent → child constraints）
   - 状态问题 → 检查 setState/notifyListeners 时序和范围
   - 生命周期问题 → 检查 initState/didChangeDependencies/dispose 顺序
   - 路由问题 → 检查路由注册、参数传递、深链配置
   - 网络问题 → 检查序列化/反序列化、超时、错误码映射

### 阶段 2：模式分析（Pattern Analysis）

**在修复之前找到模式：**

1. **找到工作示例**
   - 在同一代码库中找到类似的正常工作的代码
   - 相似实现检索（见 SKILL.md "相似实现检索"）

2. **对比差异**
   - 工作的和坏的之间有什么不同？
   - 列出每个差异，无论多小
   - 不要假设"这个不重要"

3. **检查已知反模式**
   - 对照 Red Flags 表（见下方）
   - 是否是架构问题而非实现问题？
   - 是否触碰了 project_guardrails 中的约束？

### 阶段 3：假设与测试（Hypothesis & Testing）

**科学方法：**

1. **提出单一假设**
   - 明确陈述："我认为根因是 X，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做最小可能的改动来验证假设
   - 一次只改一个变量
   - 不要同时修多个东西

3. **验证后再继续**
   - 修好了？是 → 阶段 4
   - 没修好？提出新假设
   - 不要在上面叠加更多修复

### 阶段 4：实施修复（Implementation）

**修根因，不是修症状：**

1. **先写失败测试**（如果品质锚定 >= polished）
   - 最简单的可能复现
   - 自动化测试优先
   - 必须在修复之前有

2. **实施单一修复**
   - 解决已识别的根因
   - 一次一个改动
   - 不做"顺便"改进
   - 不捆绑重构

3. **验证修复**
   - 测试通过了吗？
   - 没有破坏其他测试？
   - 问题实际解决了吗？

4. **如果修复不起作用**
   - **停下来**
   - 计数：已经尝试了几次修复？
   - 如果 < 3 次：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3 次：停下来质疑架构（见下方）**

## 3 次失败升级规则 [Rigid]

同一问题连续 3 次修复失败时，必须质疑架构假设：

**表明架构问题的模式：**
- 每次修复都揭示新的共享状态/耦合/不同位置的问题
- 修复需要"大规模重构"才能实施
- 每次修复都在其他地方产生新症状

**停下来质疑基本面：**
- 这个模式从根本上是否健全？
- 我们是否"只是因为惯性才坚持"？
- 应该重构架构还是继续修症状？

**回传 controller**，由 controller 评估是否需要回退到 S2 重新设计方案。这不是失败——这是架构层面的发现。

## Red Flags — 停下来，按流程走

如果脑中出现以下想法：

| 想法 | 现实 |
|------|------|
| "加个 null check 就好了" | 未理解为什么是 null，修复的是症状不是根因 |
| "改成 const 应该就不报错了" | 编译错误和 const 不一定相关，先读报错栈 |
| "复制那边的写法应该能用" | 上下文不同时复制等于引入未知变量 |
| "先加个 hotfix，后面再查根因" | 未调查根因的 hotfix 是下一次 bug 的种子 |
| "报错信息很清楚，不用查了" | 报错信息说的是症状，不一定是原因 |
| "上次这样改好了，这次也一定行" | 上下文不同时经验不是证据 |
| "问题很简单，不用走流程" | 简单问题也有根因，流程对简单 bug 很快 |
| "时间紧，先猜一个" | 系统性调试比猜测更快，猜错更浪费时间 |
| "先试这个，不行再说" | 第一个修复设定了模式，从一开始就做对 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因 |
| "再试一次修复"（已经试了 2+ 次） | 3+ 次失败 = 架构问题，质疑模式而不是继续修 |
| "每个修复都揭示新问题在不同位置" | 架构问题的信号，停下来重新评估 |

**所有这些意味着：停下来，回到阶段 1。**

## 合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不用流程" | 简单问题也有根因，流程对简单 bug 很快 |
| "紧急情况，没时间走流程" | 系统性调试比猜-试-猜更快 |
| "先试这个，然后再调查" | 第一个修复设定了模式，从一开始就做对 |
| "多个修复一起试，省时间" | 无法隔离哪个生效了，还会引入新 bug |
| "参考太长，我适配一下模式" | 部分理解保证出 bug，完整读完再应用 |
| "我看到问题了" | 看到症状 ≠ 理解根因 |
| "再试一次"（已经 2+ 次失败后） | 3+ 次失败 = 架构问题，质疑模式不要继续修 |

## 与 flutter-forge 体系的集成

- **与 SKILL.md 的关系**：核心原则第 14 条要求 S4 遇到 bug 时按本流程执行
- **与 engineering_heuristics.md 的关系**：提供 Flutter 专项知识基线（页面拆分、组件抽取、主流模式识别）作为调查参考
- **与 verify_agent 的关系**：S5 验证发现 bug 时，verify_agent 回传 controller，由 page_engineer 按本流程修复后重新验证
- **与 tdd_discipline.md 的关系**：阶段 4 实施修复时，如果品质锚定 >= polished，先写失败测试再修复
- **与 project_guardrails 的关系**：调查过程中发现触碰了项目护栏约束时，记录为风险并回传 controller

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因调查** | 读错误、复现、查变更、追踪数据流 | 理解是什么以及为什么 |
| **2. 模式分析** | 找工作示例、对比差异 | 识别差异点 |
| **3. 假设与测试** | 提理论、最小测试 | 确认或排除假设 |
| **4. 实施修复** | 写测试、修复、验证 | Bug 解决，测试通过 |
